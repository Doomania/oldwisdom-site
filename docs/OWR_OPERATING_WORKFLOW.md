# OWR Operating Workflow

## Non-negotiable workspace rule

`D:\Claude\Projects\oldwisdom-site` is the **only** OWR repository checkout.

- Never clone or copy the full repository for an article, campaign, QA run, or release.
- Never create duplicate site checkouts, Hermes project mirrors, or campaign roots. Channel-only historical Pinterest material belongs in the established OWR content engine, never alongside website source.
- **Never use a Git worktree for OWR.** Resolve unrelated dirty work in the canonical checkout; if it cannot be safely resolved, stop and report the blocker rather than making another workspace.
- `node_modules`, generated previews, contact sheets, browser downloads, and failed generations are temporary. They do not belong in OWR long-term storage.
- **Preflight before any write:** inspect the canonical folder map, the target bundle, `git status`, and existing assets before creating a file or folder. Reuse the approved bundle/path; never create a speculative workspace, test directory, or duplicate asset root.
- **Temporary work:** create it only when essential, inside the repository’s existing ignored temporary location, with one task-specific name. Delete test renders, contact sheets, downloads, failed generations, and obsolete test files immediately after verification; retain only release evidence required by the canonical bundle.
- **Disk efficiency:** prefer incremental Git pull/commit/push in the canonical checkout. Do not duplicate tracked files locally to make review or QA easier.

## One guide lifecycle

### 1. Intake — no writing
1. Work only in the canonical checkout.
2. Read `automation/content-queue.md`, the production inventory, and relevant live pages.
3. Confirm the reader problem, mechanism, and outcome do not overlap an existing or queued guide.
4. Create exactly one bundle: `content/production/<YYYY-MM-DD>-<slug>/`.

### 2. Draft — source bundle only
1. Create/update `ARTICLE.md`, `SOURCES.md`, `PUBLISH.json`, `ARTICLE-QA.md`, and `RELEASE.json` in that bundle. Pin copy (`PINTEREST.md`) and all other promo content go in `oldwisdomretold-social\article_pins\<bundle>\`. New bundles and any active bundle when next touched use this layout; closed historical bundles are not retrofitted.
2. `PUBLISH.json.status` uses the validator's only allowed values: `draft`, `review`, or `published`. `RELEASE.json` holds independent article/Pinterest/email gate states.
3. Do not generate final media, build, deploy, upload, schedule, or create a separate repo/workspace during this phase.

### 3. Review gate — one explicit decision
1. Validate the bundle with `python scripts/site.py check content/production/<bundle>`.
2. Present the article or the finished distribution artifact for approval.
3. Record the exact approved scope in `RELEASE.json`: `article`, `pinterest_assets`, `pinterest_schedule`, or `email_send`.
4. Approval of one scope never implies another. A prior explicit durable approval covers the named scope through its listed QA gates.

### 4. Article release — only after `article` approval
1. Create the final hero/social assets in `assets/parent-hub/<slug>/`.
2. Run the native build and checks: `python scripts/site.py build` then `python scripts/site.py check --all`.
3. Run article SEO and responsive QA.
4. Commit/push from the canonical checkout, then verify the clean live URL.
5. Set `PUBLISH.json.status` to `published`; record `article.state: live`, URL, date, and proof in `RELEASE.json`, then update the queue from that record.

### 5. Pinterest — channel work outside the site checkout

The canonical channel guide is `D:\Claude\Projects\oldwisdomretold-social\guidelines\PARENT_HUB_PIN_OPERATING_GUIDE.md`. Pin copy lives in `oldwisdomretold-social\article_pins\<bundle>\PINTEREST.md`. Record completed approval/scheduling proof in `RELEASE.json`.

### 6. Close and clean
1. Retain only the canonical bundle, final website assets, validation-only Pin copy, and release records in this checkout; channel creative/evidence remains in the OWR content-engine.
2. Delete failed generations, duplicate contact sheets, temporary downloads, `node_modules`, obsolete campaign folders, and temporary worktrees.
3. Verify `git worktree list` shows only the canonical checkout; if not, stop and report it as a blocker.
4. Do not open the next guide until the current guide is either fully closed or explicitly held at a named approval/blocker gate.

## Central register & destination integrity

- `docs/OWR_CONTENT_REGISTER.md` is the generated, read-only audit index of every schema-v2 bundle, its article state and canonical URL, and recorded Pinterest permalinks. Regenerate it with `python scripts/owr_content_register.py` after every release, schedule change, or housekeeping operation.
- A bundle’s `PUBLISH.json` and `RELEASE.json` remain the source of truth. The register never replaces them.
- Before changing, moving, or deleting a live asset, legacy asset set, or release record: confirm the guide’s canonical destination and all recorded Pinterest permalink/card records. Never change a destination URL merely to tidy files.
- The weekly audit is report-only: it identifies untracked clutter, stale generated output, missing source/release fields, broken or unrecorded destinations, and duplicate asset roots. It must not delete, deploy, reschedule, or alter social posts.

## Status vocabulary

`PUBLISH.json.status` is the website renderer state and uses only:

`draft` → `review` → `published`

`RELEASE.json` is the single operational truth. It contains separate `article`, `pinterest`, and `email` records, each with `state`, `approval`, `updated_at`, and proof (`url`, provider ID, or scheduled-card ID). Allowed channel states are `draft`, `approved`, `live`, `scheduled`, `published`, or `held`; a held channel includes `reason`.

```json
{
  "article": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "url": null},
  "pinterest": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "cards": []},
  "email": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "provider_id": null}
}
```

`automation/content-queue.md` is a readable mirror of `RELEASE.json`, not an independent decision record. Never use vague states such as “resume,” “almost done,” or “ready” without naming the next gate.

## End-of-task proof

A task is complete only when its final state is verified from the primary surface:

- article: clean production URL;
- Pinterest: exact Scheduled Pins card or published Pin URL;
- email: provider-side `Sent` state;
- cleanup: canonical path exists, temporary paths are absent, and `git worktree list` has no obsolete entries.
