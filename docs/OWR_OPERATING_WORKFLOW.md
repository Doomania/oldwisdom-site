# OWR Operating Workflow

## Non-negotiable workspace rule

`D:\Claude\Projects\oldwisdom-site` is the **only** OWR repository checkout.

- Never clone or copy the full repository for an article, campaign, QA run, or release.
- Never create `oldwisdom-*` project folders, Hermes project mirrors, campaign roots, or Pinterest archives.
- A temporary Git worktree is allowed only when the canonical checkout is genuinely blocked by unrelated dirty work. It must live under `D:\Claude\Worktrees\owr-<task>`, be removed immediately after merge/abandonment, and then be removed from Git with `git worktree remove` / `git worktree prune`.
- `node_modules`, generated previews, contact sheets, browser downloads, and failed generations are temporary. They do not belong in OWR long-term storage.

## Canonical folder map

| Path | Owner and allowed contents | Rule |
|---|---|---|
| `content/production/<YYYY-MM-DD>-<slug>/` | **Source bundle:** article, research, metadata, QA, `PUBLISH.json`, `PINTEREST.md`, `RELEASE.json`, and website-input `media/` | One folder per guide; never a second campaign folder. |
| `content/production/<bundle>/media/` | Original website hero, responsive variants, and social image named in `PUBLISH.json` | The site builder copies these into the public asset path. New Pinterest media does **not** go here. |
| `assets/parent-hub/<slug>/` | Public site-asset output copied by `scripts/site.py` | Build-managed; never manually edit hero/social copies. |
| `assets/parent-hub/<slug>/pinterest/` | Final approved Pinterest images/videos plus `APPROVAL_QUEUE.json` | The only location for active or held Pinterest media. One folder per guide; no carousel/archive sub-root. |
| `articles/`, `parents/`, `sitemap.xml`, `llms.txt` | Rendered site output | Generated by the site workflow; do not hand-edit. |
| `automation/content-queue.md` | Human-readable release index mirrored from bundle `RELEASE.json` | It is a report, never the deciding source of status. |
| `scripts/`, `templates/`, `config/`, `tests/`, `docs/` | Site implementation and durable operating documentation | Change only for a deliberate platform/workflow improvement. |
| `content/teen-guides/` | Reserved future teen-guide source seam | No Parent Hub material here. |

## Prohibited / temporary paths

- `pinterest_assets/` is legacy evidence only: no new files, no scheduling source, and no new references. Migrate only any still-active asset set into `assets/parent-hub/<slug>/pinterest/` with its release proof, then remove the legacy set.
- `output/`, `tmp/`, root `media/`, browser downloads, contact sheets, and failed generations are disposable local output. Do not commit them; delete them at task close.
- No external OWR source folders, no per-guide repository clones, and no active worktrees outside the temporary exception in the workspace rule.

## One guide lifecycle

### 1. Intake — no writing
1. Work only in the canonical checkout.
2. Read `automation/content-queue.md`, the production inventory, and relevant live pages.
3. Confirm the reader problem, mechanism, and outcome do not overlap an existing or queued guide.
4. Create exactly one bundle: `content/production/<YYYY-MM-DD>-<slug>/`.

### 2. Draft — source bundle only
1. Create/update `ARTICLE.md`, `SOURCES.md`, `PUBLISH.json`, `PINTEREST.md`, `ARTICLE-QA.md`, and `RELEASE.json` in that bundle. New bundles and any active bundle when next touched use this layout; closed historical bundles are not retrofitted.
2. `PUBLISH.json.status` uses the validator's only allowed values: `draft`, `review`, or `published`. `RELEASE.json` holds independent article/Pinterest/email gate states.
3. Do not generate final media, build, deploy, upload, schedule, or create a separate repo/workspace during this phase.

### 3. Review gate — one explicit decision
1. Validate the bundle with `python scripts/site.py check content/production/<bundle>`.
2. Present the article or the finished distribution artifact for approval.
3. Record the exact approved scope in `RELEASE.json`: `article`, `pinterest_assets`, `pinterest_schedule`, or `email_send`.
4. Approval of one scope never implies another. A prior explicit durable approval covers the named scope through its listed QA gates.

### 4. Article release — only after `article` approval
1. Create the final hero/social assets in `assets/parent-hub/<slug>/`.
2. Run the native build and checks: `python scripts/site.py build` then `python scripts/site.py check --all`.
3. Run article SEO and responsive QA.
4. Commit/push from the canonical checkout, then verify the clean live URL.
5. Set `PUBLISH.json.status` to `published`; record `article.state: live`, URL, date, and proof in `RELEASE.json`, then update the queue from that record.

### 5. Pinterest — only after the live URL and `pinterest_assets` approval
1. Create the agreed final images in `assets/parent-hub/<slug>/pinterest/`; retain only final approved files, their metadata, and QA evidence.
2. Default format is one clear static Pin per approved image. Do not switch to carousel, video, batch, or another format mid-task.
3. A non-default format requires a documented, proven end-to-end scheduling path before Eric is asked to approve it. If the platform cannot complete it reliably, hold the assets; do not convert one approved format into another without approval.
4. Before scheduling, verify Pinterest account identity, destination URL, board, image hashes, existing scheduled inventory, and collision-free slots.
5. Schedule only the approved assets, then read back the exact scheduled cards. Record their IDs/dates and proof in `RELEASE.json`, then update the queue from that record.

### 6. Close and clean
1. Retain only the canonical bundle, final website assets, final approved/queued Pinterest assets, and release records.
2. Delete failed generations, duplicate contact sheets, temporary downloads, `node_modules`, obsolete campaign folders, and temporary worktrees.
3. Run `git worktree prune` and verify that the canonical checkout is the only permanent OWR workspace.
4. Do not open the next guide until the current guide is either fully closed or explicitly held at a named approval/blocker gate.

## Status vocabulary

`PUBLISH.json.status` is the website renderer state and uses only:

`draft` → `review` → `published`

`RELEASE.json` is the single operational truth. It contains separate `article`, `pinterest`, and `email` records, each with `state`, `approval`, `updated_at`, and proof (`url`, provider ID, or scheduled-card ID). Allowed channel states are `draft`, `approved`, `live`, `scheduled`, `published`, or `held`; a held channel includes `reason`.

```json
{
  "article": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "url": null},
  "pinterest": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "cards": []},
  "email": {"state": "draft", "approval": null, "updated_at": "YYYY-MM-DD", "provider_id": null}
}
```

`automation/content-queue.md` is a readable mirror of `RELEASE.json`, not an independent decision record. Never use vague states such as “resume,” “almost done,” or “ready” without naming the next gate.

## End-of-task proof

A task is complete only when its final state is verified from the primary surface:

- article: clean production URL;
- Pinterest: exact Scheduled Pins card or published Pin URL;
- email: provider-side `Sent` state;
- cleanup: canonical path exists, temporary paths are absent, and `git worktree list` has no obsolete entries.
